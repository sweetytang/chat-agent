# Research: 旧项目到 lui-agent 的完整功能迁移矩阵

- Query: 只读审计 `apps/chat-agent`、`apps/chat-agent-self`、`apps/branching-chat`，建立迁移到 `lui-agent` 的功能、代码证据、行为和验收矩阵
- Scope: mixed（内部代码、任务设计和依赖版本；未引入外部网页资料）
- Date: 2026-07-31

## Findings

### 阅读范围与目标模块约定

本矩阵以当前任务的设计稿为目标边界：FastAPI 是唯一 API 入口；Python LangGraph 只负责图编排；PostgreSQL 负责用户、线程、运行、消息、checkpoint、interrupt；前端通过 fetch + SSE 消费版本化业务事件，事件 reducer 是状态唯一入口。目标模块名沿用 [design.md](../design.md) 的规划：`backend/app/modules/auth`、`threads`、`runs`、`checkpoints`、`interrupts`，`backend/app/graph`、`integrations/llm`、`integrations/tools`、`common`，以及前端 `services/sse`、`store/run`、`store/thread`、`store/message`、`domain/branching` 和对应组件。

### 三个旧项目的能力归属与差异结论

### 迁移优先级与建议的端到端验收顺序

1. 先固定 `auth → thread → run.queued/started → message.delta/completed → run.completed/failed` 合同，用 fake model + PostgreSQL 验证用户隔离、事务和回放。
2. 再加入 tool call/result 与 HITL interrupt/resume，验证 approve/reject/edit 以及 stale request/checkpoint。
3. 在同一 checkpoint 合同上加入 sibling、branch selector、edit/regenerate，验证旧分支不可被新 head 覆盖。
4. 加入 queue/stop/cancel 和刷新恢复，明确 PRD 中“无消息队列基础设施”与设计中“run queue”的最小实现范围。
5. 最后接 reasoning/DeepSeek、structured output、generative UI 和真实 provider；这些应由统一 message/event decoder 接入，不应绕过 reducer 写 UI 状态。

## Caveats / Not Found

- 三个旧项目没有独立的自动化测试目录/测试文件，本文验收场景是根据可观察行为和代码路径整理，不能视为现有测试已经覆盖。
- `chat-agent-self` 与 `branching-chat` 依赖根目录 `prisma/schema.prisma`，该 schema 的 datasource 是 SQLite；不要把它当作 PostgreSQL 目标 schema 的直接迁移文件。
- 旧项目没有后端持久化的独立 `runs` 表，也没有 sequence/version 事件日志；queue、stop、断线重连和 run 终态需要在 lui-agent 重新设计和测试。
- 旧项目的部分“编辑”行为是前端从消息元数据找到 parent checkpoint 后重新 submit，并非独立的 edit endpoint；目标 API 需要明确命令语义，但仍应保持“旧版本保留、新分支生成”的用户可观察行为。
- `chat-agent` 的 presentation tools 会通过占位 ToolMessage 让图结束，`chat-agent-self` 则在 controller/service 中串接工具执行；这两种运行模型不能并行作为目标真相，必须由新的 graph/run service 统一。
- 未审计产品代码之外的部署、外部 provider 账号、生产反向代理和数据库迁移历史；它们不影响能力矩阵，但会影响上线验收。
