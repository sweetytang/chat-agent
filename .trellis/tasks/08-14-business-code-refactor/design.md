# 业务重构设计

## 原则

- 先锁定行为，再改变结构；优先删除和拆分，不增加无收益抽象。
- 格式化、机械清理、结构拆分和缺陷修复是不同批次。
- 公开 API、DTO、SSE、数据库、主题和 MCP 现有行为是不可破坏合同。
- 只使用迁移后工作区内有效业务代码作为范围。

## 重构批次

### 1. 机械质量清理

使用 Ruff/Prettier/ESLint/Stylelint/TypeScript/Mypy 统一格式、导入和未使用符号。只接受工具可证明的等价修改，不顺手改逻辑。

### 2. 死代码审计

| 证据 | 处理 |
| --- | --- |
| 用户明确确认废弃 | 直接删除并跑完整门禁 |
| 无静态引用，且不在路由/注册/配置/脚本/生成入口 | 删除并补必要回归验证 |
| 可能由动态导入、插件或外部入口使用 | 保留，直到获得运行证据 |
| 仅测试引用 | 判断测试是否锁定有效合同；不能只为删实现而删测试 |

### 3. 超限文件拆分

- 后端 `api/runs.py`：路由只保留 HTTP/SSE 边界；请求/响应模型、运行编排、恢复/取消和事件输出按现有职责拆到 `modules/runs`，不改变 endpoint 和事件顺序。
- 前端 `McpSettings/index.tsx`：页面容器保留组合与顶层状态，表单、Server 列表/卡片、导入区和对话框按独立交互职责拆成同目录组件及 CSS Module。
- 前端 `useMcpSettings.ts`：保留页面协调 hook，将 JSON 解析、Server CRUD、刷新和开关等可独立测试逻辑拆到 domain/service hooks；不改变请求时序和错误状态。

具体文件名以实现前代码搜索为准，不为达到行数而制造薄包装。

### 4. 缺陷处理

- 阻断核心链路、数据正确性或安全：先写失败测试，再修复。
- 与当前重构直接相关的小缺陷：已有或新增明确测试时修复。
- 无关非阻断问题：记录后续，不在本任务实现。
- 行为修复单独成批，不能藏在格式化或移动 diff 中。

## 验证模型

每批修改先跑模块测试，再跑所属工作区全量门禁。后端跨层修改检查 API→Service→DB/Graph→SSE；前端检查 Service→Store→Projection→Component。最终运行双 CI 和关键浏览器流程。

## 回滚

- 每个模块批次保持独立，可通过反向小补丁恢复，不影响已验收迁移。
- 测试锁定失败时先回退结构修改，不通过放宽断言掩盖行为变化。
- 发现范围外合同变化时停止并回到规划，不继续扩大重构。
