# 按生成顺序流式展示全部事件

## 目标

把对话页从“历史消息区 + 底部附加状态/卡片”改为统一的流式时间线，使用户能够按 Agent 实际生成顺序理解消息、推理、工具与交互事件。

## 背景与已确认事实

- 当前 `Chat` 先完整渲染 `history`，再依次渲染等待态、单一 `reasoning` 和 `presentationItems`，因此非消息内容无法插入消息之间，只能出现在对话页底部（`frontend/apps/web/src/modules/chat/components/Chat/index.tsx:210-311`）。
- 当前运行状态把消息、推理和展示卡片存入不同字段：`history`、单一累加字符串 `reasoning`、按 `sequence` 排序的 `presentationItems`（`frontend/apps/web/src/modules/runs/store/run.ts:21-35,113-191`）。
- `presentationItems` 已能按 `runId + sequence` 保留多条工具结果、审核、结构化输出、Generative UI 和错误卡片；“同类型只显示一张”并非所有卡片的通用事实，但推理仍只有一个聚合块，`tool.call` 也完全没有进入展示投影（`frontend/apps/web/src/modules/presentation/domain/items.ts:3-14`，`frontend/apps/web/src/modules/runs/store/run.ts:71-78,116-137`）。
- SSE 协议已经为每个运行事件提供单调递增的 `sequence`，可作为单次运行内的顺序依据（`frontend/apps/web/src/modules/runs/types/events.ts:9-41`）。
- 后端会交错产生推理、消息、工具调用/结果、审核、结构化输出、Generative UI、错误以及运行/检查点生命周期事件；当前历史接口只持久化对话消息，刷新后不能从历史快照恢复完整运行时间线。
- 多线程改造已将运行投影按 `threadId` 隔离；本需求不能退化并行线程、切换线程、停止、审核恢复和终态历史校准行为。

## 需求

- 建立统一的可渲染时间线投影，不再由 `Chat` 按数据类型分区追加。
- 时间线展示合并后的语义条目，包括用户消息、推理块、助手消息、工具调用及结果、审批、结构化输出、Generative UI 和错误。
- `run.started`、`message.delta`、`checkpoint.created`、`thread.updated` 等内部协议事件只驱动状态，不直接成为可见条目。
- 时间线中的可见条目严格遵循事件生成顺序。
- 同一语义内容的增量事件应流式更新对应条目，而不是每个 delta 新建一张卡片。
- 同类型语义事件可重复出现，并保留各自位置与稳定身份。
- 一次工具调用对应一张具有稳定身份的生命周期卡片：`tool.call` 创建，审批、执行结果或失败原地更新；同一工具的多次调用必须生成多张独立卡片。
- 每段连续推理对应一个独立时间线条目：首个 `reasoning.delta` 创建并在生成期间展开，后续增量原地追加；`reasoning.completed` 后自动折叠，用户可重新展开；后续推理创建新条目而非覆盖旧条目。
- 同一助手轮次可包含多个文本段：连续消息 delta 更新当前文本段；一旦被推理、工具、审批、结构化输出、Generative UI 或错误等语义条目打断，后续助手文本必须在该条目之后创建新文本段，视觉上仍归属同一轮助手回复。
- 完整语义时间线必须持久化；页面刷新、重新进入会话或切换回来后，应恢复消息以外的推理、工具、审批、结构化输出、Generative UI 和错误条目。
- 运行中刷新不自动重连或续流；刷新应保留已生成内容，把断开的运行明确投影为已中断并提供重试入口。
- 时间线必须完整支持 checkpoint 分支：新分支继承分叉点之前的共同条目并追加自己的运行条目；旧分支后续条目继续保留；切换分支时不得混入其他分支的推理、工具或展示内容。
- 保留现有消息编辑、重新生成、分支切换、审核、失败重试与多线程隔离能力。
- 流式时间线采用智能跟随：用户位于底部附近时自动滚动；用户主动向上阅读后停止抢占视口并显示“有新内容/回到底部”入口；回到底部后恢复自动跟随。
- 不兼容旧 `history/messages` 展示与状态逻辑；统一时间线成为前后端唯一的会话内容事实来源，不保留双轨投影或 fallback。
- 允许破坏性删除旧 `Message` ORM/数据库表、messages/history API、checkpoint `messages` state 以及已有消息数据；不提供数据迁移或读取兼容。
- 模型上下文、线程标题、消息编辑、重新生成和分支控制全部从统一时间线派生。
- 按事件合同、纯投影器、持久化服务、API DTO、前端 reducer 和展示组件分层；模块职责单一，禁止把 payload 解析或状态转换堆进 `Chat`、卡片组件或请求函数。
- 保持实现简洁、可测试，并复用仍符合新合同的现有卡片组件。

## 验收标准

- [x] 当一次运行按“推理 → 消息 → 工具调用 → 工具结果 → 消息”产生内容时，页面按相同顺序展示，不把工具卡片统一挪到底部。
- [x] “助手文本 → 工具 → 助手文本”渲染为两个有序文本段和中间的工具卡片，不把后续文本追加到工具卡片之前。
- [x] 连续 delta 原地更新所属语义条目，条目顺序和 React key 保持稳定。
- [x] 推理生成期间可实时阅读，完成后自动折叠；多段推理均保留在各自生成位置。
- [x] 同一次运行内多次出现同类工具或展示事件时，每次均在正确位置可见。
- [x] 工具卡片从调用、等待审批、执行中到成功/失败始终保持原位置和同一稳定身份。
- [x] 切换线程后，各线程仅展示自己的实时投影；切回运行中线程可继续接收增量。
- [x] 编辑、重新生成、审核恢复、停止和最终历史刷新不产生重复、错序或残留条目。
- [x] 用户在底部时能持续看到最新流式内容；向上滚动后阅读位置保持稳定，并可一键回到底部恢复跟随。
- [x] 页面刷新或重新进入会话后，已持久化时间线条目及其相对顺序与刷新前一致；运行中刷新不自动续流，并显示已中断状态及重试入口。
- [x] 编辑旧消息、重新生成或切换 checkpoint 后，页面只展示当前分支的完整时间线；切回旧分支可恢复旧轨迹。
- [x] `run.started`、delta 包、checkpoint 与 thread 生命周期事件不会作为原始卡片污染页面。
- [x] 现有消息编辑、重新生成、审批恢复、停止、多线程并行与终态快照校准测试继续通过。
- [x] MCP 工具审批恢复必须在新请求 Session 中持久化工具结果和 assistant 终态；刷新后不得回退到不可点击的等待审批卡片。
- [x] 前后端不存在同时维护 `history` 和 `timeline` 的双事实来源；模型上下文、编辑、重新生成和标题生成均从统一时间线派生。
- [x] 数据库迁移后不存在旧 messages 表；前后端不存在旧 messages/history API、类型、Store 字段和兼容分支。

## 技术约束

- SSE `sequence` 只保证单次运行内顺序；跨运行和跨分支顺序必须由持久化时间线快照表达。
- checkpoint state 只保存带版本的 timeline 快照，不再保存平行 messages 快照。
- 组件只渲染类型化语义投影，不直接解析原始 SSE `data`。
- 事件字段的归一化、幂等判断和条目生命周期转换必须各自集中在单一边界，不能散落在卡片组件中。
- 保持现有 `version: 1` 外层事件合同；允许为现有事件补充稳定语义条目标识字段。

## 范围外

- 不实现刷新后的活动运行重连、事件重放、断点续传或 `Last-Event-ID`。
- 不逐条展示原始协议事件。
- 不兼容旧 history API、旧 checkpoint state 或旧前端 Store 结构。
- 不迁移、保留或恢复升级前已有的消息数据；执行数据库升级前的数据备份由部署方自行负责。
- 不重做现有卡片的完整视觉语言；仅补齐统一时间线、生命周期状态、推理折叠和智能滚动所需交互。
